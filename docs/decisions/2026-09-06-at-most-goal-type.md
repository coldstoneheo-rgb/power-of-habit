# 결정 기록 — 이하 목표(AT_MOST) 유형 부활 (2026-09-06)

2026-09-05 결정 기록이 사용자에게 남긴 질문 "AT_MOST를 살릴지, 살리면 '미수행=0=성공' 의미 충돌을 어떻게 풀지"에 대해 사용자가 **부활**을 선택했다(2026-09-05 밤).
의미 설계는 전문가 역할 3인(아키텍트 / 디자이너·PO / QA)의 의견을 퍼실리테이터가 취합해 아래로 확정했다.

## 확인된 사실
- `RecordOutcomes.of(habitType, status, inputValue, targetValue)` 한 함수가 4개 렌더러·3개 저장 경로의 판정을 담당한다. 여기에 방향 하나만 더하면 전 화면이 따라온다.
- 통계 엔진은 status 캐시(COMPLETED/FAILED/SKIPPED)만 본다. 저장 경로가 `statusForValue`를 쓰므로 방향은 저장 시점에 캐시로 반영된다 — 엔진 수정 불필요.
- 이상 목표에서 값 0은 "미수행"(NONE)이다. 이하 목표에서는 0이 가장 좋은 결과라 같은 규칙을 쓸 수 없다 — 바로 이 충돌이 지난 세션이 부활을 보류한 이유다.
- 등록 화면의 이상/이하 라디오는 c1b99e5(7월)에 있었으나 저장되지 않는 죽은 UI였고 #28에서 숨겼다. DB에 방향 컬럼은 없다.

## 결정 — 의미

| 질문 | 아키텍트 | 디자이너·PO | QA | 합의 |
|---|---|---|---|---|
| 기록하지 않은 날 | 미수행. "안 적으면 성공"은 통계를 조용히 부풀리고 체크형·이상형과 다른 예외 규칙을 엔진에 심는다 | 미수행이지만 **입력 UI가 0 입력을 유도**해야 한다("0도 기록하세요") | 미수행. 성공으로 치면 습관을 잊은 사용자가 스트릭을 받는다 — 데이터 신뢰성 위반 | **미수행(NONE)**. 사용자가 0을 직접 적는다. 입력 다이얼로그와 등록 화면에 문구로 안내 |
| 기록한 0 | 성공(0 ≤ 목표) | 성공 — 이하 목표의 핵심 사례(담배 0개비) | 성공. 음수·NaN은 미수행 | **성공** |
| 한도 초과(값 > 목표) | 기존 PARTIAL 재사용. "기록했지만 목표 미달성"이라는 뜻으로 일반화하면 새 상태·새 색이 필요 없다 | 색은 기준미달과 같은 `partial(accent)`. 방향이 다르면 "초과"라는 것은 목표 표기("5개비 이하")가 말해 준다 | PARTIAL → FAILED 캐시. 미기록과 구분되므로 "적었는데 실패" 추적 가능 | **PARTIAL 재사용**(의미: 목표 미달성 기록). 새 status·새 색 없음 |
| 목표 없는 이하 습관 | 등록 화면에서 막는다(0보다 큰 목표 필수) | 같음 | 이전(JSON)으로 들어온 무목표 이하 습관은 "적은 값은 전부 성공"으로 관대하게 | 등록에서 **필수**, 판정 폴백은 **값 ≥ 0 이면 성공** |
| 저장 | DB v5 `targetType TEXT NOT NULL DEFAULT 'AT_LEAST'`. 부호 인코딩(음수 목표) 같은 꼼수 금지 | — | 옛 행은 전부 AT_LEAST → 기존 동작 무변경. JSON 형식은 필드 추가만(formatVersion 1 유지, `ignoreUnknownKeys`) | **v5 마이그레이션 + DTO 기본값 필드** |

**가장 강한 반대(QA):** "PARTIAL이 두 뜻(기준미달·초과)을 가지면 색만 보고는 구분이 안 된다." → 메인 셀과 1x1 위젯은 목표를 그리지 않으므로 색만으로는 실제로 구분되지 않는다(자체 리뷰 지적). 그래도 사용자는 자기 습관이 "이하"인지 알고 있고, 상세 화면·입력 다이얼로그가 "5 개비 이하"를 보여 주므로 값("7 개비")과 함께 읽으면 뜻이 잡힌다. 별도 상태를 도입하면 4개 렌더러·대비 테스트·위젯 팔레트가 모두 늘어나는 비용이 더 크다고 판단해 유지.

## 자체 리뷰 뒤 덧붙인 규칙
- **방향·목표를 바꾸면 기존 기록의 status 캐시를 다시 계산한다**(`RecordOutcomes.restatusAfterTargetChange`, 등록 화면 저장 트랜잭션 안). "엔진 수정 불필요"는 저장 시점 캐시가 전제라, 이 재계산이 없으면 통계(캐시)와 캘린더(값)가 서로 반대를 말한다. 건너뜀·값 없는 기록은 건드리지 않는다.
- **미기록 표시**: 이하 목표에서는 "기록한 0(성공)"과 "안 적음(미수행)"이 같은 "0"으로 보이면 안 되므로 메인 셀·1x1 위젯의 미기록 자리는 대시(–)다. 이상 목표는 기존 "0" 유지.
- **JSON 이전**: 이하 습관이 든 파일만 formatVersion 2로 내보낸다(옛 앱은 "업데이트하라"를 본다). 가져오기에서 기존 습관에 매칭된 수치 기록은 **기존 습관의** 목표·방향으로 status를 다시 맞춘다.
- **판정 함수의 방향 매개변수에 기본값을 두지 않는다** — 새 호출자가 방향을 빠뜨리면 컴파일이 막는다.
- **Drive 복원**은 백업 DB의 user_version이 앱 스키마보다 높으면 거부한다(v5 백업을 v4 앱에 넣으면 실행마다 죽는다).

## 구현 범위(이 PR)
- `HabitEntity.targetType`(기본 `AT_LEAST`), `AppDatabase` v5, `MIGRATION_4_5`.
- `RecordOutcomes.of/statusForValue`에 `targetType` 매개변수(필수) — 호출 10곳이 `habit.targetType`을 넘긴다. `targetLabel`로 목표 표기 통일.
- 등록 화면: 목표 필드 옆 **이상/이하** 칩, 이하 선택 시 안내 문구, 0보다 큰 목표 필수 검증.
- 상세 화면 목표 표기 "5 개비 이하", 입력 다이얼로그 보조문 "목표 5 개비 이하 (0도 기록하세요)".
- JSON 이전 DTO `targetType` 필드(옛 파일은 AT_LEAST로 읽힘).
- 테스트: `RecordOutcomesAtMostTest`(판정 7케이스), `HabitTransferTest`(라운드트립·옛 파일 기본값).

## 하지 않는 것
- 새 status 문자열, 새 RecordOutcome 값, 위젯 색 추가, 통계 엔진 변경.
- "기록 없음 = 성공" 옵션. (요청이 오면 습관별 옵트인으로 별도 결정.)
- 기존 습관의 방향 일괄 변경(사용자가 수정 화면에서 바꾼다).
